# Typed coordination rule tower V1

Run:

    python3 ~/FIM/pipeline/shg_rule_tower.py
    python3 ~/FIM/pipeline/shg_typed_web.py <printed-run-directory>

## Implemented boundary

This is a bounded second-order construction demonstration. The Python harness constructs a complete rule object from a fixed checked template, admits exactly that template to its active registry, binds an addressed native seed occurrence, allocates fresh declaration identities, interprets a construction program, and asks the original Goggles SHG producer to materialize the successor.

It is not native Goggles rule discovery, general proof admission, self-hosting, provider dispatch or VM instruction execution. The construction interpreter and rule registry are new bounded harness code, not asserted preexisting Goggles capabilities. The native relation/machine/SHG storage, incidence, addressing, persistence and registry owners remain Goggles.

The isolated native checkout is `~/ORCHESTRATION/worktrees/goggles-vm-feedback-47fe6800`, based on commit `47fe6800307c8921a4b733ad6e56fa0b78698de8`. The shared PR192 checkout remains untouched. Exact modified native-file digests and source changes are retained with every successful run.

## Complete generated rule

The generated rule has explicit match, typed parameter declarations, fresh-allocation declarations, preconditions, production program, obligations and typed input/output interface. Its identity covers all these fields. Admission rejects missing correspondence, unsupported construction semantics, altered identity and missing obligations. Rule inputs map through a boundary map to production-program inputs; parameter substitution is a separate interpreter operation.

Bindings have disjoint classes:

- Matched: current native body/occurrence address and root graph identity.
- Parameter: positive iteration bound, effect set, contract reference and correlation type reference.
- Fresh: child graph, participant placements, operation/node-type definitions, machine, relation intents and port definitions.

Fresh IDs are deterministic allocation identities derived from the rule identity, matched native address and allocation name. Their ownership scopes are explicit. They are declaration intent IDs; final canonical native row identities and H002 coordinates are generated by Goggles afterward.

## Construction semantics

`append` adds a typed declaration or relation intent to the staged region. Constraint-bearing records and predicates use ordinary declarations; there is no additional bracket opcode.

`nest` stages a child SHG declaration at the matched open occurrence body. It does not infer match bindings, rule parameters or boundary maps.

`enclose` supplies a total parent/child port correspondence. The native producer checks direction, type, contract and effects. In meta-construction, enclosure explicitly maps typed rule interface ports to the nested construction-program interface, not to an arbitrary parameter collection.

The seed is an abstract run occurrence with state/result boundary and open body. The rule grows a nested loop region containing controller and abstract step-callee occurrences, typed request/completion ports, a machine and two distinct hyperrelations:

- CALL: caller, argument, result, return; typed aggregate arguments/results and explicit callee operation.
- ACTIVATION-FEEDBACK: controller, activation, completion, continuation; explicit machine, work-call relation, correlation schema and finite iteration bound.

Both have exactly one participant in each declared role. The request pair and completion pair are type-compatible, but request and completion are different types. Call and feedback share their participants while retaining distinct constitution identities and semantics.

Types, effects, contracts, ports, operations, machines and relation dependencies form the web. Containment is only one projection.

## Native additions

The opt-in SHG system loads `lisp/shg_activation_feedback_v1.lisp`. The SHG declaration producer accepts the explicit CALL and activation-feedback profiles, registers native A002 constitutions, checks their role/type/ownership/effect constraints, and preserves their machine/correlation/work references in native relation records and application parameters.

The feedback constitution uses native relation kind CONTROL with a specific activation-feedback constitution; CALL uses native CALL. No unrecognized generic relation kind is smuggled into the base registry.

Repeated machine transitions can share dependencies. Dependency materialization is idempotent for the same source/target/reason. Dependencies targeting native relations use participant kind RELATION, not MEMBER.

## Machine and guard semantics

The native machine contains five explicit transitions:

| State | Event / typed guard | Successor | Effects |
|---|---|---|---|
| ready | issue / positive budget | waiting | activate, await |
| waiting | matching completion / continue and budget remains | ready | publish |
| waiting | matching completion / budget exhausted | terminated | publish, terminate |
| waiting | matching completion / halt | terminated | publish, terminate |
| waiting | matching completion / trap | terminated | terminate |

Guard type declarations identify their state/completion inputs and Boolean result. Native validation checks the fixed profile's guard signatures, transition shape, trigger and effects. The bounded protocol interpreter evaluates these declared guards against its actual budget and supplied completion data; it does not execute unknown predicates.

Correlation compares graph generation, input generation, invocation, iteration and attempt. Wrong keys, wrong key types, duplicate completion and unknown events are rejected before state changes. Trap does not publish a replacement carried state.

The trace supplies abstract completion payloads. It demonstrates coordination semantics for this bounded interpreter, not the correctness of a future VM step implementation or eventual completion from an external worker.

## Publication and evidence

Native construction validates, persists/reloads, resolves every generated coordinate and replays the declarations. Old-generation addresses are rejected against the successor. The isolated driver retains original successful native checks, with process-local identity memoization only for immutable construction/traversal; declaration replay is still performed.

Only after all checks pass does the harness atomically rename a local accepted-graph pointer to the retained native artifact. This is local conditional publication; durable crash-atomic storage and a shared live graph store are not claimed.

Each run retains:

- Checked template and complete generated rule.
- Meta-construction trace and structural rule-admission receipt.
- Matched/parameter/fresh binding environment.
- Interpreter trace, graph delta and source-to-output rule/binding identities.
- Seed and successor native SHG objects, headers, indexes and generated exports.
- Graph validation receipt and local accepted-graph pointer.
- Runtime transition trace and category-specific negative checks.
- Actual R001 address lookup receipts for every generated address.
- Exact native source digests and changes.

Structural validation does not prove behavioral refinement, eventual completion or eventual termination without environmental assumptions. Those obligations remain open. Executable routing authority remains unbound.

## Acceptance exercised

The initial native graph has 154 addressed members. Applying the generated/admitted rule grows it to 421, with a nested loop region, native CALL and CONTROL hyperedges, machine transitions and dependency web. Two matching completions publish successive carried states and terminate at budget exhaustion. Halt and trap exits are checked separately.

Negative checks cover missing rule correspondence/obligations, invalid iteration bounds, unknown events, mistyped correlation keys, all five mismatched correlation components, duplicate completion, missing hyperedge role, incompatible argument type, undeclared effect, missing transition, invalid guard type and incomplete boundary.

Branch, async, wait/join and broader network templates are next vocabulary members. They are not implemented by this loop/call demonstration.
